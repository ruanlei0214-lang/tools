## Context

`remote` 模块现在的配置来源是三份编译进产物的 JSON：`config/config.json`（连接与超时）、
`config/io.json`（IO 点位）、`config/register.json`（寄存器点位）。`loadSettings()` 在
`newService()` 里跑一次，把结果存进 `Service.settings`，之后全程只读。前端 `Config()`
拿到这份快照，`IoPanel` / `RegisterPanel` 按 `tab.groups` 渲染，`setInterval` 在挂载时
按 `refreshIntervalMs` 起一次。

于是「改配置」等于「改源码 + 重新构建 + 换 exe」。而点位表是现场每换一套夹具就要动的东西。

同一个仓库里已经有一个先例：`board` 的指令按钮存在 `%APPDATA%\embedtools\board-commands.json`，
界面上直接增删改，整份送回后端校验落盘，再拿后端写进去的那份当准。这一版照这个路子做，
但要多处理两件 `board` 没遇上的事：配置有一份出厂默认要播种，以及「立即生效」要覆盖到
正在跑的定时器和超时。

约束：模块之间不许互相引用，所以不能复用 `board` 的任何代码；改动要尽量少，不顺手重构。

## Goals / Non-Goals

**Goals:**

- IO 与寄存器点位在界面上增删改，两页共用同一套控件，保存后当前页立即重画。
- 连接参数（地址、端口、路径、两个超时、刷新间隔）可改、存下来、按各自的时机立即生效。
- 现场配置与出厂默认分离：出厂默认仍编译进产物，现场配置落在 `%APPDATA%`，可逐份恢复默认。
- 某一份配置坏掉只影响它自己，页面其余部分照常可用，且坏文件不被覆盖。

**Non-Goals:**

- 不做 JSON 文本编辑框。校验过的表单能拦住负数端口和越界 `pulseMs`，文本框只能在保存时整份报错。
- 不做配置的导入导出、备份多版本、跨机同步。要搬到另一台电脑就手动拷那三个文件。
- 不做点位的拖拽排序。顺序按清单顺序，需要调整就改端口或重建那一行。
- 不做「保存后自动重连」。这个页面上的按钮会动现场的气缸，换设备的时机必须由人决定。
- 不下沉跨模块的配置读写公共层。只有两个使用方（`board` 与 `remote`），形态也不一致。

## Decisions

### 现场配置放 `%APPDATA%\embedtools\`，编译进产物的那三份降级为出厂默认

三个文件名对应现有三份：`remote-config.json`、`remote-io.json`、`remote-register.json`。
加载顺序是「`%APPDATA%` 有就用它，没有就用内嵌那份」。

**替代方案：写回 `internal/modules/remote/config/*.json`。** 做不到——那三份是
`//go:embed` 进二进制的，运行期没有这些文件。

**替代方案：放 exe 旁边。** 否决。exe 可能落在 Program Files 或只读共享盘上，那里写不进去。
`netcfg/state.go` 和 `board/commands.go` 已经各因为这个理由选过 `%APPDATA%`。
代价是拷走 exe 不带走配置，用「界面上显示完整路径」来补。

### 三份文件不合并成一份

**替代方案：一份 `remote.json` 装下全部。** 否决。分开的好处直接对应两条 spec 要求：
逐份「恢复默认」不牵连其他两份，以及某一份坏掉时另两份照常可用。合成一份之后，
IO 点位表里少个逗号会把连接参数一起废掉。

拆分也让文件布局和编译进产物的那三份一一对应，翻起来不用换脑子。

### `Service.settings` 加独立的读写锁，不复用 `s.mu`

`settings` 从「构造时读一次的常量」变成可变状态，被 `requestTimeout()`、`connectTimeout()`
以及新增的保存方法读写，而这些调用发生在不同的 goroutine 上。

用一把独立的 `cfgMu sync.RWMutex`，读取时拷一份快照出来。**不复用现有的 `s.mu`**：
`s.mu` 保护的是连接与强制标志，`client()` 持它，而 `requestTimeout()` 在
`client()` 返回之后被调用。把两者混进一把锁，日后谁在持锁期间顺手读一次配置就死锁。
两把锁各自职责清楚，代价是多一个字段。

### 保存以「整份面板」为单位，由后端校验后落盘，前端拿后端写进去的那份当准

前端把改完的整个 `Tab`（含所有分组与点位）送回后端；后端跑与加载时同一套
`parsePanel` + `normalizeTab` 校验，通过才原子落盘，然后把归一化后的那份返回给前端。

**替代方案：按点位增删改各开一个方法。** 否决。三个方法要各写一遍校验，还要处理
「改到一半失败」的中间态。整份替换只有成功和失败两种结果。

**替代方案：前端本地改完就认，后端只负责写盘。** 否决。归一化（类型转大写、名称缺省补
`DO15`、`onValue`/`offValue` 补 `1`/`0`）发生在后端，前端自己算一遍迟早和后端对不上。
`board/commands.go` 的 `SaveCommands` 就是这么做的。

校验复用现有函数，**不新写一套保存专用的校验**：两套校验规则迟早分叉，那时候「能存进去
但打不开」的配置就出现了。

### 写盘先写 `.tmp` 再改名

同目录内改名是原子的。直接往目标文件上写，进程在写一半时挂掉就留下半份 JSON，
下次打开整份配置读不出来。`board/commands.go` 已经这么做。

### 「恢复默认」的实现是删掉 `%APPDATA%` 那份文件

删掉之后加载逻辑自然退回内嵌的出厂默认，不需要第二条「把默认值写进文件」的路径。
删文件失败要如实报错，不能界面上显示成默认值而盘上那份还在，下次打开又变回去。

### 坏文件退回默认但不覆盖，告警按文件分别攒起来

某一份读不出来或过不了校验时，只有那一部分退回内嵌默认，其余照常。告警文字带上文件名与
行号——`describeParseError` 已经能给出行列号，现在只需要把文件名拼进去。

**不覆盖坏文件**：现场手改出的错，那个文件里可能还有能人工救回来的点位。这一点和
`board` 对损坏的按钮清单的处理一致。

多份同时出问题时，告警拼成一条显示。顶部那条状态槽是「配置告警优先于操作结果」的，
现有 `RemoteView` 的 `status` computed 已经是这个规则，不用改。

### 前端：两个面板共用一个编辑组件，放在 remote 模块内

新增 `frontend/src/modules/remote/PointEditor.vue`，`IoPanel` 与 `RegisterPanel`
都用它，靠一个 `types: string[]` 之类的 prop 区分可选类型，以及一个端口标签文字。

**替代方案：两个面板各写一份编辑表单。** 否决。「两页对齐」是明确的 spec 要求，
写两份就是让它们各自漂移——改了 IO 的字段顺序忘了改寄存器那边，界面立刻不一致。

组件放在 `frontend/src/modules/remote/` 下而不是提到共享层：它只服务这一个模块，
提上去等于给别的模块也开了个口子，违反「不做超出当前需求的抽象」。

### 刷新定时器改成跟着间隔重建

`IoPanel` / `RegisterPanel` 现在在 `onMounted` 里按 `props.intervalMs` 起一次定时器，
注释里写着「配置只在启动时读一次，所以它在本组件的生命周期里不会变」。这句话现在不成立了。
改成 `watch(() => props.intervalMs)`，变了就清掉旧定时器重起一个，那条注释一并改掉。

### 地址类改动不自动重连，只提示

保存主机地址、端口、路径之后，当前连接保持原样，界面提示要点「连接」才用新地址。
自动重连会让「刚才那一下发到哪台设备上了」说不清——这正是本模块一开始就决定不做自动重连的理由。

超时与刷新间隔不同：它们不改变连着谁，直接对下一次请求 / 下一次轮询生效即可。

## Risks / Trade-offs

- **界面保存会整份覆盖盘上那份，现场同时手改文件的改动会丢** → 保存是整份替换而非合并，
  这是「前端拿后端写进去的那份当准」的必然结果。文档里写明：要手改就先关程序，
  或者改完在界面上点一次刷新配置再动手。

- **拷走 exe 不会带走配置** → 界面显示配置文件所在位置，要搬机器就手动拷那三个文件。
  这是选 `%APPDATA%` 换来的代价，`netcfg` 与 `board` 已经付过同样的代价。

- **点位可以在界面上无限加，加多了一次读全部点位会变慢** → 现有 `refreshIntervalMs`
  的 200ms 下限拦的就是「刷得比控制器答得快」。真加到几百个点位时症状是刷新变慢，
  不是请求堆积，可接受；不预先加点位数量上限。

- **端口号能填但控制器不认（如 `DI31`）** → 已有的 `describeWriteError` 会解释
  「读的时候不报错、写才被拒」，这一版不额外校验端口上界：那个范围是实测出来的、换机型会变，
  写死在校验里反而会拦住别的设备。

- **`settings` 变成可变状态之后，一次操作中途配置被改** → 每次操作开头取一份快照，
  整个操作用同一份值。不追求「改完立刻影响正在进行的那次请求」。

- **多一把锁** → 换来的是不必推理「哪个方法能在持 `s.mu` 时读配置」。两把锁职责不重叠。

## Migration Plan

1. 首次运行时 `%APPDATA%` 下没有这三个文件，加载走内嵌出厂默认，界面与现在完全一样，无告警。
2. 用户第一次保存时才生成对应文件。没保存过的那几份继续用出厂默认。
3. 编译进产物的三份 JSON 内容不动，只是语义变成「出厂默认」，所以旧版本的行为
   等价于「一份现场配置都没有」的新版本，不需要任何迁移动作。
4. 回滚：删掉 `%APPDATA%\embedtools\remote-*.json` 三个文件即可退回出厂默认，
   界面上的「恢复默认」做的就是这件事。

## Open Questions

- 点位与分组的顺序调整（上移/下移）要不要做？这一版按清单顺序，不提供调序入口。
  等现场真的抱怨顺序不好用了再加，那时也才知道是要调点位还是调分组。
- 连接参数编辑区放在连接区那一行里展开，还是收进一个「设置」入口？倾向前者——
  连接区刚压缩成一行，再挂两个超时和刷新间隔会把它撑回两行。实现时按界面实际效果定。
