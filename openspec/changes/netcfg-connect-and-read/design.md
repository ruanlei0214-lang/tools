## Context

设备连接卡片原有三个按钮：「测试连接」「读取网口」「一键恢复网络」。前两个在实际使用里永远连着点，第二下不承载决策。页面打开时自动测连接的行为是早先加的，它让这个冗余更刺眼——自动测完只剩一句「连接成功」，表格空着等用户补一下点击。

这件事在 `netcfg-cleanup` 的 design.md 里曾被列为 Non-Goal 并否决过，理由是"属于行为变更，不是清理"。那个判断针对的是**该不该塞进清理变更**，不是该不该做。现在单独立项做。

## Goals / Non-Goals

**Goals:**

- 把固定的两连点收成一次点击。
- 页面打开即得到可操作的网口表格。
- 界面上不留指向已删按钮的文案。

**Non-Goals:**

- 不改后端任何方法的行为。
- 不改「一键恢复网络」的位置与语义。
- 下发配置成功后不自动重连。

## Decisions

### 保留 `TestConnection`，不直接用 `ListInterfaces` 顶替

合并后 `test()` 依次调 `TestConnection` 和 `ListInterfaces`，两次独立短连接。看上去 `ListInterfaces` 自己也要 dial、失败也会报错，似乎可以省掉前一次。

否决：省掉之后，"连不上"和"连上了但 `ip addr show` 跑不出来"两种失败会挤在同一次调用里，只能靠错误文本区分。分成两步时，第一步的失败一定是连接问题，第二步的失败一定是设备侧命令问题——现场排查方向完全不同，这个区分值一次握手。

代价是每次点击两次握手，页面打开时也是两次。局域网内单次握手在百毫秒级，可以接受；真成为问题时再合并，那时也应该先把错误分类做好。

### 读网口失败盖掉「连接成功」

`test()` 里先 `await TestConnection` 再 `await ListInterfaces`，成功提示放在最后写。所以后一步抛错时，用户看到的是读取失败的原因，而不是「连接成功」。

这是有意的：连上了但读不到网口，用户接下来什么都做不了，报「连接成功」等于给一个用不上的好消息，还会让人以为可以继续操作。

### 清空旧网口放在连接开头，不放在失败分支

`test()` 一进来就把 `ifaces`、`selected`、`confirming` 清掉，成功后再填回，而不是在捕获到错误时才清。

放在开头更简单：不用给 `call()` 加针对某个操作的失败回调，也不用在 `test()` 里套一层 try/catch 再重新抛出。而且语义上更准确——连接进行中设备状态本来就是未知的，这段时间显示一份上次的表格没有依据。成功路径上没有差别：成功后 `select()` 本来就会重写表单。

失败原因不做区分。超时、认证失败、地址不可达，任何一种之后屏幕上那份数据都同样不可信；只清超时那一种，反而会让另外两种失败留下更隐蔽的坑。

### 「测试连接」升为主按钮

原来的主按钮是「读取网口」。删掉它之后，卡片上只剩一个正向操作和一个危险操作；如果正向操作还是次级样式，视觉重心会落在「一键恢复网络」这个删文件的按钮上。

### 按钮名保持「测试连接」

它现在做的事比"测试"多。考虑过改成「连接并读取网口」之类。否决：名字变长，而用户对这个按钮的心智模型本来就是"连上设备开始干活"，读网口是连上之后的自然结果，不需要写进按钮名。

### 下发成功后不自动重连

下发后设备正在换地址，脚本里还有 `sleep 1`，立刻重连大概率失败，反而会给一条误导性的错误。保持由用户决定什么时候点「测试连接」确认，只把提示文案里失效的按钮名改掉。

## Risks / Trade-offs

- **页面打开就会拉网口列表，比原来多一次设备侧命令** → `ip addr show` 与 `ip route show` 都是只读命令，没有副作用；用户本来打开页面就是要看这些。
- **失去了"只验连通性、先不碰设备"的轻量选项** → 原本「测试连接」可以在不读取任何东西的情况下探一下。实际使用中没有这个需求：这个页面的存在意义就是改地址，不存在只想 ping 一下的场景。
- **连接慢时，整个流程的等待变长（两次握手 + 两条命令）** → 按钮在 `busy` 期间禁用并显示「连接中…」，反馈是连续的，不会出现无响应的空窗。

## Migration Plan

纯前端改动，无数据无配置迁移。回滚即还原 `NetcfgView.vue`。
