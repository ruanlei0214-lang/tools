## Context

工具箱里已经有 `netcfg` 通过 SSH 管这台设备的网口，`board` 是同一台设备、同一条 SSH 通道上的
另一半工作：跑命令、传文件。所以技术上没有新路要探，真正要定的是几处取舍——用什么传文件、
用户攒出来的按钮存哪、以及哪些操作该拦。

约束来自 `openspec/specs/module-independence/spec.md`：不能 import `netcfg`，共享逻辑要么下沉
共享层要么各写一份；代码要精简，不为假想需求预留。

### 设备侧的实测情况

规划期间连上 `192.168.1.136` 只读地探了一遍，下面这些是量出来的，不是推断的：

| 项 | 实测值 |
| --- | --- |
| SSH 服务 | `SSH-2.0-OpenSSH_8.6`（**不是** dropbear） |
| SFTP 子系统 | **可用**，`/usr/libexec/sftp-server` 存在（133184 字节） |
| 认证 | 用户 `root`、空密码，直接通过 |
| 内核 | `Linux 4.14.61-rt37`，主机名 `ZMC900E-Linux` |
| 用户态 | BusyBox v1.33.0，登录 shell `/bin/sh`（ash） |
| 常用目录 | `/opt` 下有 `runtime/`、`autorun.sh`、`setBridge.sh`、`zlgmaster` 等 |

这一步值得做：原本的设计假设「很可能是 dropbear、未必有 sftp-server」，整个文件传输方案
都建在这个假设上。实测把它推翻了，于是下面的传输决策换了一套——这比在现场发现再改便宜得多。

## Goals / Non-Goals

**Goals:**

- 连接凭据（IP、端口、用户名、密码）全部在界面上可见可改，空密码能直接连。
- 指令按钮在界面上增删改，重开程序还在。
- 远端目录能列、文件能上传下载删除，路径可随时改。
- 文件操作全程不经过 shell：路径不拼命令，就没有引号和空格的问题。
- 危险操作（删除、覆盖）有一道明确的确认，但不替用户禁掉他要做的事。

**Non-Goals:**

- 不做终端仿真：不提供交互式 shell、不支持需要 tty 的命令（`top`、`vi`）。
- 不做传输进度百分比、断点续传、目录递归上传下载。
- 不做命令白名单或危险命令拦截。这是给现场用的运维工具，root 登录本身就意味着能做任何事，
  拦一半只会让人绕过去。
- 不做「记住密码」。这台设备密码是空的，为它加一处凭据落盘等于凭空造一个泄露点。
- 不做 SSH 密钥登录。当前需求是空密码的 root。
- 不为「万一某台设备没有 SFTP」预留第二套传输实现。见下面第一条决策。

## Decisions

### 文件操作全部走 SFTP

设备上有 `sftp-server` 且子系统握手成功（见上表），所以直接用 SFTP，依赖
`github.com/pkg/sftp`。这是**推翻了原方案**之后的选择，原方案是用 SSH exec 通道加 `cat`
传文件、加 `ls -lA` 解析列目录。

SFTP 在三件事上明显更好：

1. **列目录不用解析文本**。`client.ReadDir` 直接给 `[]os.FileInfo`，名称、大小、是否目录
   都是结构化的。原方案要解析 `ls -lA` 的输出，而那份输出的格式随实现和 locale 变，
   带空格的文件名、符号链接、`total` 行都得单独处置——实测的 `/` 目录里就有
   `lib64 -> lib`、`linuxrc -> bin/busybox` 两个符号链接，正好是解析最容易错的地方。
   换成 SFTP，这个解析器和它的一整套 fixture 测试都不存在了。
2. **路径不经过 shell**。`cat > <path>`、`rm <path>` 要把用户填的路径拼进命令里，
   全靠一个 `quote()` 函数兜着；引号或转义写错一次，操作对象就静默地变成了别的文件。
   SFTP 的路径是协议参数，不存在这个类别的错误。
3. **错误是结构化的**。SFTP 回的是「权限不足」「文件不存在」这类状态码，而不是一段
   要拿去猜的 stderr 文本。

代价是多一个依赖，以及绑定了「设备上有 sftp-server」这个事实。

**不做「先试 SFTP、失败退回 cat」**：那意味着两套传输实现，而退路那套在这台设备上永远跑不到,
坏了也没人会发现。真换了一台没有 SFTP 的设备，那时再按实测情况改——比现在养一条测不到的
代码路径划算。这条也写进了非目标。

### 命令执行仍然走 SSH exec，不走 SFTP

SFTP 只管文件。指令按钮那部分照旧开 session 跑命令，一条命令一个 session。
两者共用同一条 SSH 连接：`sftp.NewClient(sshClient)` 就是在这条连接上再开一个 channel。

### 上传和下载都是先写临时文件再改名

`sftp.Create` 会当场把目标文件截断——一旦传到一半断掉，那个文件就变成了半个，
而它可能是设备正在运行的东西（实测 `/opt` 下就摆着 `zlgmaster`、`autorun.sh` 这类）。

所以上传写 `<目标>.tmp`，`io.Copy` 完成且 `Close` 成功之后再 `client.Rename` 顶上去；
失败就把临时文件删掉，原文件一个字节都没动。下载同理：先写本地 `<目标>.part`，
成功后 `os.Rename`，失败删掉。

`Rename` 在同一文件系统上是原子的。注意 SFTP 的 `Rename` 在目标已存在时可能失败，
需要先 `Remove` 目标——所以顺序是「传 `.tmp` → 删原文件 → 改名」，
而这个「删原文件」只在临时文件已经完整落盘之后才发生。

### 下载靠 `Stat` 的大小验证完整性

SFTP 能在传输前拿到文件大小，所以下载完成后比一次字节数。这是 `cat` 方案给不了的：
流式读到 EOF 时分不清「文件读完了」和「连接断了」，只能靠退出状态间接判断。

### 一条长连接，每次命令开一个 session

SSH 协议里一条 session 只能跑一条命令，但连接可以复用。每点一个按钮现连一次既慢，
又让设备侧不断新建会话。所以连接显式建立、显式断开，中间所有命令和文件操作共用它。

**不做自动重连**：藏在每次调用背后重连，会让「刚才那条命令到底发出去了没有」
说不清楚——而这里的命令是重启进程、删文件这种做过就回不去的事。连接断了就如实退回未连接。

### 按钮清单存 `%APPDATA%\embedtools\board-commands.json`

不放 exe 旁边：exe 可能落在 Program Files 或只读共享盘上，那里写不进去。
`netcfg/state.go` 已经因为同样的理由选过这个目录，这里跟着它，不另发明一处。

代价是拷走 exe 不会带走按钮。**所以界面上直接把这个文件的完整路径显示出来**，
要搬到另一台电脑就手动拷它——比做一套导入导出便宜得多，而且现场看得懂。

同目录不构成模块间交互：`board-commands.json` 只有 board 读写，`netcfg-state.json` 只有 netcfg 读写，
两个模块没有共享任何一个文件。

### 按钮清单写入用临时文件加改名，写失败要报到界面

和 netcfg 记地址那份的处置**故意不同**。netcfg 记的是「上次连通的 IP」，丢了只是下次退回默认值，
所以它直接 `os.WriteFile`、失败只记日志。按钮清单是用户一条条攒出来的，丢了没法自动恢复，
而且保存是用户的显式动作——他按了保存，就得知道成没成。

所以：先写同目录临时文件再 `os.Rename`（避免写一半崩溃把清单变成残缺 JSON），
失败时把错误抛回界面。

### 清单文件损坏时退回空列表并告警，不覆盖那个坏文件

解析失败只让按钮区空着并显示一条告警，页面其他功能照常。**不自动重写**：
那个文件里可能还有人工能救回来的命令，覆盖掉就真没了。告警里带上文件路径，好让人去看。

用户此后主动添加按钮时确实会覆盖它——那是他看到告警之后的选择，可以接受。

### 命令原样下发，不在本地解析

命令整条交给设备的 shell（实测是 BusyBox ash），管道、重定向、`&&` 都由设备解释。
本地不做任何改写或过滤：用户写的是给这台设备的命令，工具替他猜等于让界面上看到的和实际执行的
不是一回事。

这条和「文件操作不经过 shell」并不矛盾：命令是用户自己写的、他知道会被 shell 解释；
而文件路径是他在列表里点出来的，不该因为名字里有个空格就变成两个参数。

### 删除只从列表里选，不给「输入路径直接删」的入口

root 加删除的组合下，打错一个字的后果无法挽回。界面上不提供直接输入路径删除的入口——
删除只能作用于刚刚列出来、用户眼睛看见过的那一行，确认框里显示完整路径。

用 `client.Remove`，它对非空目录会直接失败，所以不存在「递归删掉一棵树」这种可能。
选中目录时把 SFTP 回的错误原样显示，不在本地拦——本地判断得依赖列表里那个可能已经过期的
`isDir`。

**不做根目录白名单**。现场要看的目录不止一个（`/opt`、`/opt/runtime`、`/config`、`/tmp` 都可能），
写死一个根等于每次换目录都要改代码；真正的闸门是「只能删列出来的东西」加确认框。

### 命令输出一次返回，不用事件流

一条命令跑完再把 stdout / stderr 整段返回，不做逐行推送。Wails 的 `EventsEmit` 是全局事件总线，
模块独立规格明确点名禁止用它跨模块通信；即使只在模块内部用，也要为它想一套不撞名的事件名。
当前的命令都是秒级的，不值得。

代价写进已知限制：长时间运行的命令在跑完之前界面上看不到任何输出。

### `ssh.go` 与 netcfg 重复的那部分照抄一份，不下沉共享层

`dialWithin` 那套「超时必须盖住 TCP 建连、SSH 握手、认证三段」的处理，netcfg 已经写过一次，
board 需要一份一样的。模块独立规格允许两种做法：下沉 `internal/module`，或各写一份。

现在各写一份。下沉要先想清楚共享层的形态（超时策略、认证方式、host key 策略要不要参数化），
而目前只有两个使用方、且 board 还要在这条连接上叠一个 SFTP 客户端，netcfg 不需要。
真出现第三个使用方时再上提——那时也才看得清该抽什么。

## Risks / Trade-offs

- **绑定了「设备上有 sftp-server」** → 已在真机确认（OpenSSH 8.6 + `/usr/libexec/sftp-server`）。
  换机型或设备被裁剪过时会整块失效，所以连接失败的报错要能明确区分「SSH 连不上」和
  「SFTP 子系统起不来」，让现场一眼看出是哪一层的问题。
- **多一个依赖 `github.com/pkg/sftp`** → 它只依赖已经在用的 `golang.org/x/crypto/ssh`，
  没有引入新的传递依赖树。
- **大文件传输期间界面只能显示「正在传输」** → 传输在后端 goroutine 里跑，界面不冻结，
  但没有百分比。SFTP 拿得到总大小，以后要加进度条不用改接口形状。
- **root 加原样下发命令等于全权** → 这是工具的目的，不是缺陷。不加白名单；
  危险集中在「删除」这一条明确路径上，用确认框加「只能删列出来的」两道闸门收口。
- **空密码加 `InsecureIgnoreHostKey`** → 与 netcfg 同一取舍：内网嵌入式设备没有稳定主机密钥，
  且这台设备的 IP 正可能被本工具改过。风险边界是「必须在同一内网」。
- **按钮清单换机器不跟着走** → 界面上显示文件路径，手动拷。不做导入导出。
- **上传不保留权限位** → `/opt` 下的脚本实测是 `rwxrwxrwx`，上传后新文件不会自动带上执行位。
  现在不做权限设置界面：真需要改权限，用指令按钮跑一条 `chmod` 更直白。这条要写进已知限制。

## Migration Plan

新增模块，没有数据迁移。

1. `go get github.com/pkg/sftp`。
2. 先落后端，`go test ./internal/...` 过（含 `internal/modules/boundary_test.go` 的模块边界检查）。
3. 再落前端，`wails generate module` 生成绑定。
4. `modules.json` 的 `all` profile 加上 `board`，跑 `go run ./tools/genmodules -profile all` 接线。
5. `wails build` 出产物，在真机上按 tasks.md 最后一节的清单验一遍。

回滚：从 `modules.json` 移除 `board` 并重跑生成器，产物里就不会再有它——
模块独立约束保证这一步不牵动其他模块。彻底回滚再删掉那两个目录，并把
`github.com/pkg/sftp` 从 `go.mod` 里 `go mod tidy` 掉。

## Open Questions

- 主板上是否有需要 tty 才能跑的日常操作？如果有，「不做终端仿真」这条非目标要重新评估。
- 常用的远端路径是哪几个？实测 `/opt` 下摆着 `runtime/`、`autorun.sh`、`setBridge.sh`、
  `zlgmaster` 这些，看起来 `/opt` 就是主战场，所以默认路径先定 `/opt`。
  如果现场固定在三五个目录之间切，值得在配置里放一个候选列表做成下拉。
- 上传脚本之后要不要自动补执行位？现在的答案是「不要，用指令按钮跑 `chmod`」，
  但如果现场每次上传都得跟一条 `chmod`，就该重新考虑。
